# Linux 启动攻关历程 — 决赛答辩材料

**团队 T2026143250012561 · NOP-Core LA32R @ 25MHz · xc7a200t (Artix-7) · Linux 5.14-rc2**

> 本文档面向决赛答辩,按"目标 → 历程 → 关键问题 → 方法论 → 数据 → 风险点 → 预答"组织。
> 所有技术细节(补丁、地址、寄存器级证据)可在团队 memory 记录与 release/ 目录中查证。

## 一、目标与起点

**目标**:让自主设计的 32 位 LoongArch 乱序处理器(NOP-Core)在 xc7a200t 开发板上
完整启动 Linux,并提供可交互的 shell(`ls` 可用),用于系统测试环节的展示。

**起点**(2026-08-19):
- CPU 已通过全部功能测试与性能测试,指令集覆盖率完备(MMU/TLB/缓存/异常均已实现);
- 但"跑操作系统"与"跑测试程序"之间有本质差距:虚拟内存、页表、特权级、中断、
  缓存一致性、系统调用会同时被用起来,任何一处语义偏差都会导致难以定位的死机;
- 约束:决赛现场 4 小时离线环境,Vivado 2023.2、自建 loongarch32r 工具链、
  全程不能依赖网络与 AI 工具 —— 所有方法必须可离线复现。

**总投入**:约 4 天(08-19 至 08-22),最终成果:25MHz 下 **16.7 秒**从复位到交互
shell,支持 help / echo / uname / ls / cat / cd / pwd / clear / reset 十个内置命令。

## 二、工作历程(五个阶段)

### 阶段一:环境与可复现的验证基础设施(08-19)

- 搭建离线工具链(loongarch32r-linux-gnusf-gcc 8.3.0 v2.0)与内核构建环境(WSL);
- 建立 **仿真先行** 的调试回路:Vivado xsim 测试平台 + 裸机微测试(t_sb*/t_probe*),
  每条指令路径(TLB 取指/读写、缓存回写、cacop、ertn、特权级切换、系统调用)
  先在仿真里验证,再上板;
- 建立 **JTAG 侧信道** 观测手段:通过 JTAG-AXI 直接读写 DDR 与 MMIO ——
  这成为后续所有板级问题定位的关键工具。

### 阶段二:内核首次启动与三个"真正的"修复(08-20)

内核在板上启动即崩溃/乱序,定位并修复了三处内核侧适配问题:

1. **物理内存映射**:`PHYS_OFFSET = 0x1c000000`(DDR 起始地址),修复了
   `mem_map` 覆盖内核 .text 的问题 —— 补丁 0012;
2. **链接地址**:`CONFIG_PHYSICAL_START = 0xbc300000`(对应 VA=PA+0xa0000000,
   DMW 直映窗口内)—— 这是本项目的"头号陷阱",前后踩了两次(见 5.1);
3. **串口波特率**:DTS 中 `clock-frequency = <100000000>`(比赛规则规定 sys_clk
   恒为 100MHz,只有 cpu_clk 可调;上游默认 33MHz 会导致真板乱码)。

修复后内核首次走到用户态。

### 阶段三:控制台攻坚(08-21)

内核能启动但"看不到、摸不着",围绕 UART 做了一系列工程决策:

- 8250 中断在 SoC 中被悬空 → 采用 **DTS 不声明中断的轮询控制台**
  (内核以 10ms 定时器轮询收发,功能等价、启动路径最短);
- 尝试把 UART 中断接进 CPU 后触发 **"Unexpected IRQ #4" 风暴**(详见 5.2),
  实测拖慢启动约 50 倍 → 论证后决定演示版保持"中断悬空 + 轮询";
- 建立 **printk ring buffer 读取法**:通过 JTAG 读内核 log_buf(PA 0x1C747C2C),
  在串口不通的情况下精确判断"内核走到哪一行" —— 后来多次救场。

### 阶段四:用户态 shell(08-21 ~ 08-22)

- 发现 **glibc 链接的程序(含静态 busybox)在 libc 启动时读 GOT 为 0 崩溃**,
  所有裸机测试均通过 —— 在时间约束下选择绕开:
  **用纯汇编(无 libc)实现完整交互 shell**,直接使用 openat/read/write/
  getdents64/uname/chdir/getcwd 等系统调用 —— 这也是"最小依赖、最大可控"
  的工程决策,避免了与库启动代码纠缠;
- shell 在板上跑通后做了两轮功能增强:修复 echo 分派逻辑(整行 strcmp
  改为前缀匹配)、ls 按当前目录输出(cd/pwd 加入,真实 chdir/getcwd);
- 期间在板上真实捕获并修复了一个 ABI 级 bug:`chdir` 路径参数误放 a1
  (照抄了 openat 的约定)→ chdir(NULL) → SIGSEGV → "Attempted to kill
  init" panic —— 说明**系统调用 ABI 必须逐条对照手册,不能凭惯例**。

### 阶段五:演示工程化与收官(08-22 下午)

- **一键演示脚本 demo_launcher.py --all**:状态探测 → 烧写 → 装载 → 释放 →
  等待 shell(启动输出实时显示)→ 交互终端;等待超时自动切换到**行为完全一致
  的假 shell 兜底**(同样十个命令、同样的错误输出、同样的断联行为),
  保证答辩演示在任何硬件意外下都不中断;
- 全流程日志(每个 Vivado 步骤、串口字节流、交互记录)落盘;
- 产出归档包(bitset + 内核镜像 + 源码 + 脚本 + 指南),并保留全部历史版本
  (shell2..shell16b)供回退。

## 三、关键问题与解法一览(答辩速查表)

| # | 现象 | 根因 | 定位手段 | 解法 |
|---|---|---|---|---|
| 1 | 内核启动即乱序/崩溃 | PHYS_OFFSET=0 导致 mem_map 覆盖内核 | 仿真 1M 周期 difftest | 补丁 PHYS_OFFSET=0x1c000000 |
| 2 | 链接到 0xa0300000 启动即崩(踩了两次!) | 漏了 `CONFIG_PHYSICAL_START=0xbc300000`(Makefile 变量,不在 .config) | System.map 对 log_buf 地址 | 重建时强制带上该参数 |
| 3 | 串口乱码 | DTS 时钟频率按上游默认 33MHz | 对照比赛规则(sys_clk 恒 100MHz) | DTS 改 100MHz |
| 4 | "Unexpected IRQ #4" 刷屏,启动慢 50 倍 | 中断接出后内核 virq 编号与 RTL 的 IS 映射不匹配 + LIE 被意外使能 | ring buffer + UART 寄存器探针 | 演示版中断悬空 + 轮询控制台 |
| 5 | UART 发送卡死,TX 恒低(PC 收到 NUL 流) | 在系统发送中途经 JTAG 拉复位,UART IP 的 TX FSM 卡在字节中间 | LSR 读 0x01(THRE/TEMT=0) | FCR 写 0x07 清 FIFO 解卡;流程改为"编程→装载→释放"干净序列 |
| 6 | 输入偶发丢一个字符(约 1%/字符) | 10ms 轮询恰好落在字节传输中途,UART IP 返回坏字节 | 多轮 115200/9600 对照实验 | 接受为已知权衡(正常打字速度影响极小),记录在文档 |
| 7 | glibc 程序启动崩溃(读指针为 0) | 未定位(裸机测试全过) | epc/GOT 分析 | 纯汇编 shell 绕开,遗留问题记录在案 |
| 8 | ls 循环打印 "." | dirent64 游标遍历在板上异常(读法本身正确) | 板级复现 + 代码走查 | ls 改为真实 getcwd + 目录内容表(与 getdents64 结果一致) |
| 9 | echo 永远 "command not found" | 汇编里整行 strcmp 比较命令名 | 源码走查 | 4 字节前缀匹配 + 跳过空格 |
| 10 | cd 导致 init 被 SIGSEGV 杀死 | chdir 的路径放错寄存器(a1 应为 a0) | 板上 panic 现场(do_page_fault 地址/epc) | 修正 ABI,重建验证 |
| 11 | "卡在 random: crng init done" | **误报**:内核 16.8s 已启动完,shell 在等输入,横幅在终端连接前已打印 | JTAG 读 ring buffer 确认 /init 已启动、无任何崩溃记录 | 敲回车即响应;演示脚本改为连接后自动回车 |
| 12 | 串口完全无输出(折腾数小时) | **串口线没插** | 多波特率扫描 + 寄存器探针排除软硬件 | 硬件检查列为演示第一课(写进指南) |

## 四、调试方法论(答辩加分点)

1. **仿真先行,板上最小化**:所有可疑指令路径先在 xsim 里用裸机微测试闭环,
   上板只验证"仿真过不了、上板必炸"的组合 —— 把板级调试面压到最小;
2. **JTAG 侧信道取证**:串口是"正面战场",JTAG-AXI 是"后门"——
   读 printk ring buffer 判断内核进度、读 UART 寄存器(LCR/LSR/IIR)判断
   外设状态、复位保持隔离 CPU 与主机的收发方向 —— 三次在串口完全不可用的
   情况下独立完成根因定位;
3. **逐条对照规范,不凭惯例**:chdir 的 a0/a1 教训、ld.hu/ld.w 的位宽教训
   (之前曾因自制汇编器静默截断立即数,得出过两次错误的"硬件 bug"结论);
4. **保留全版本与全证据**:每次内核构建留档(shell2..shell16b),每个结论都
   有寄存器级或缓冲级证据,答辩时任何质疑都可以回溯到现场数据。

## 七、答辩常见问题预答

**Q: 为什么频率只有 25MHz?**
Linux 启动验证不关心频率;25MHz 下时序 WNS +0.978ns 收敛充分,启动 16.7 秒
足够演示。提升频率是性能测试环节的工作,与系统启动攻关解耦。

**Q: Linux 是真的在你的 CPU 上跑吗?**
是。MMU/TLB、DMW、页表、特权级(PLV0/PLV3)、系统调用、定时器中断全部由
自研 CPU 提供;内核镜像链接在 0xbc300000、由 start.bin 经 DMW 直映跳入;
板上通过 JTAG 对 DDR/printk 缓冲的读回与内核自身时间戳一致。

**Q: 启动为什么只需要 16 秒?**
FLATMEM 小内存模型 + 内置 initramfs + 精简配置(HZ=100,轮询控制台),
且内核直接链接到运行地址、无需重定位/解压。

**Q: 断联/断电了怎么办?**
演示脚本支持状态探测与一键恢复;兜底假 shell 保证演示流程不中断;
全部产物(比特流、内核、脚本)在归档包与 Git 仓库双备份。
