# 预取（Prefetch）策略研究

> 在真实 chiplab benchmark 上用 `cpu_model` 量化多种预取策略，并给出针对当前
> SpinalHDL 乱序核（单阻塞 refill FSM、无 MSHR、按序 LSU）的落地建议。

## 1. 预取策略谱系

| 策略 | 原理 | 适用 | 硬件成本 |
|------|------|------|---------|
| **Next-line（下一行）** | 访问行 L 时预取 L+1 | 顺序/流式访问 | 极低（一个加法 + tag 比较） |
| **Stream（流）** | 检测连续 miss 流，预取 N 行 | 顺序流 | 低（几个流检测器） |
| **Stride（步长）** | 学习 PC 的访存步长，预取 addr+stride×k | 大步长（列访问、结构体数组） | 中（RPT 表） |
| **Signature-path（SPP）** | 用最近 miss 序列做"签名"预测下一个 miss | 不规则/指针追逐 | 高（签名表） |
| **Branch-target（取指）** | 预测到 taken 分支时预取目标行 | 代码跳转 | 低 |

关键区分：
- **next-line 是 stride≤line_size 的特化**：顺序访问（步长 4B/8B）时，next-line
  直接预取下一 64B 行；而 stride 预取器若 degree 太小，预取地址仍在当前行内，无效。
- **污染（pollution）**：把预取数据直接塞进 L1 会顶掉有用行；用**独立流缓冲
  （stream buffer）**可避免。

## 2. 模型与实验设置

- 预取引擎：访问触发 → 生成地址 → 入预取队列 → 后台按 `dram_latency+burst`
  完成填入 L1（或独立流缓冲）；命中流缓冲视为命中（不阻塞）。
- 8 个访存/综合 benchmark，每个 40 万条真实指令。
- 策略：none / next-line 度 1·2·4·8 / stride 度 1·4 / 流缓冲 next-line。

## 3. 结果（fireye_A0，访存密集，MPKI 30.8）

| 策略 | IPC | DCache MPKI | 说明 |
|------|-----|-------------|------|
| 无预取 | 0.352 | 30.8 | 基线 |
| next-line 度1 | 0.540 | 3.43 | **+53%** |
| next-line 度4 | 0.562 | 1.49 | **+60%** |
| stride 度1 | 0.375 | 26.0 | 几乎无效（步长小，预取仍在同行） |
| 流缓冲 next-line 度1 | 0.540 | 30.8* | +53%，但**不污染 L1** |

\* 流缓冲下 MPKI 仍 30.8（L1 需求访问仍 miss），但 8219 次由流缓冲命中直接服务，
不阻塞；"有效"缺失（真正阻塞）大幅下降。

## 4. 结论与推荐

1. **next-line 预取是当前核性价比最高的选择**：合计 IPC +15%（0.527→0.606），
   流式 benchmark 更显著——fireye_A0 +53%、fireye_D1 +39%、inner_product +18%。
   硬件成本几乎为零（一个加法 + tag 比较）。
2. **度 1 是甜点，度 ≥8 会反噬**：度 8 时 stringsearch IPC 0.484→0.458、dhrystone
   0.701→0.688，因预取污染 L1（stringsearch MPKI 1.25→3.49）+ 浪费 DRAM 带宽。
   度 2 相对度 1 仅 +0.3%（0.606→0.608），不划算。
3. **用流缓冲（stream buffer）而非直接塞 L1**：收益等同 next-line（0.605 vs
   0.606），但**不污染 L1**、不顶掉常驻数据；对"流式+常驻数据"混合负载更稳。
4. **stride 预取器在本套件上不如 next-line**（度4 才 0.589 < nextline 0.606）：
   这些 benchmark 以顺序小步长为主，stride 在步长≤line 时预取仍在同行内；
   只有大步长负载（矩阵列访问、结构体数组）才值得上 RPT。

## 5. 针对当前 RTL 的落地建议（SpinalHDL）

当前 DCache 是**单阻塞 refill FSM + 按序 LSU**，预取要能"后台"填而**不阻塞
需求访问**。最省事的做法：

**方案 A（推荐）：独立流缓冲 + 空闲时预取**
1. 加一个 `StreamBuffer`（如 4–8 项 × 64B 的寄存器/FIFO，或复用一组 BRAM）。
2. DCache 需求 miss 时，除现有 refill 外，把 `addr + line_size` 压入预取队列。
3. 一个独立状态机在 **dBus 空闲**（无需求 refill）时，从预取队列取地址、发 AXI
   突发，把行填入流缓冲（不写 L1）。
4. 需求访问先查 L1，miss 再查流缓冲；命中则"提升"到 L1 并直接回送数据。
   - 这样预取与需求 refill 共享同一 dBus，但**只在空闲时抢带宽**，不影响关键路径。

**方案 B（更简单，收益略低）：L1 内预取，仅 refill FSM 空闲时**
- 需求命中时（FSM 空闲）直接对 `addr+line_size` 做一次 tag 查询，miss 则触发
  refill FSM 填下一行。
- 优点：几乎零新增硬件；缺点：预取与需求 miss 串行，且污染 L1。

**方案 C（取指侧）**：ICache next-line + 分支目标预取——真实 benchmark 中 ICache
MPKI 大多 <6（stringsearch 11.8、dhrystone 5.8），收益远小于 DCache 预取，可作为
第二优先级。

## 6. 边界与后续

- 模型假设预取有独立填充路径（MSHR/流缓冲），未建模 dBus 端口争用；方案 A 的
  "空闲时预取"正是为规避该争用。
- 建议在 RTL 上用 difftest + 实际 perf benchmark 验证，并关注 DRAM 带宽占用
  （度 4/8 在带宽敏感时会回吐收益）。
