# DCache 流缓冲预取 —— RTL 改动清单

> 目标：在不阻塞需求访问、不污染 L1 的前提下，加 next-line 预取。
> 对象文件：`src/vivado_cannot/src/pipeline/mem/DCachePlugin.scala`（588 行）。
> 结论先行：核心改动是 (1) 新增一个小 `StreamBuffer` 模块，(2) 给 `cacheRefillFSM`
> 加一个"从流缓冲提升"的状态，(3) 加一个只在 `dBus` 空闲时跑的 `prefetchFSM`。
> 面积 ≈ 512B 存储 + 几百触发器，不碰 105MHz 关键路径。

## 0. 现状关键事实（改动的锚点）

| 信号/结构 | 位置 | 说明 |
|-----------|------|------|
| `dBus = Axi4(...)` | L21 | 唯一的 DCache AXI 端口，被读 refill 与写回共享 |
| `dataRAMs`（`SDPRAM(BWord(), lineWords*sets)`）| L28 | 数据按 word 寻址，写地址 = `idx @@ rspId` |
| `infoRAM` + `wPort` | L31/L127 | tag/lru/dirty，写口 `wPort` |
| `dataWs` / `dataMasks` | L128-129 | 各 way 的数据写口 / 字节掩码 |
| `replaceWay` / `idx` / `tag` | L157/124/125 | 替换路 / 物理 index / 物理 tag |
| `valids` / `dirtyBitsManager` | L25/26 | 有效位 / 脏位 |
| `cacheRefillFSM` | L398 | 需求 miss：`waitAXI→readMem→commit→finish` |
| `dirtyLineWritebackFSM` | L204 | 脏行写回，stateBoot 时 `writebackIdle := True` |
| `storedWord` | L165 | 填充当前 word 的寄存器，load 前传用 |

**dBus 空闲** = `cacheRefillFSM` 在 `stateBoot` **且** `writebackIdle`（即写回 FSM 也在
stateBoot）。预取只能在这个窗口用 `dBus`。

## 1. 新增模块 `StreamBuffer.scala`

放 `pipeline/mem/` 下，或复用 `blackbox/mem` 的 SDPRAM。参数化 `entries=8, lineWords=16`。

```scala
class StreamBuffer(lineWords: Int = 16, entries: Int = 8) extends Component {
  val io = new Bundle {
    val reqAddr = in UInt(32 bits)               // 需求 miss 的物理地址
    val sbHit   = out Bool()                      // 命中
    val sbData  = out Vec(BWord(), lineWords)     // 命中行的 16 个 word（提升用）
    val hitWay  = out UInt(log2Up(entries) bits)

    val pfAddr  = in Stream(UInt(32 bits))        // 预取请求（行地址）
    // 预取填充端口（prefetchFSM 逐 word 写）
    val fillValid = in Bool()
    val fillWay   = in UInt(log2Up(entries) bits)
    val fillWord  = in UInt(log2Up(lineWords) bits)
    val fillData  = in BWord()
  }
  val tags  = Vec(Reg(UInt(20 bits)), entries)         // tag = addr[31:12]
  val valid = Vec(RegInit(False), entries)
  val data  = Vec.fill(entries)(Vec(Reg(BWord()), lineWords)) // 8×16×32bit = 512B 寄存器
  val roundRobin = RegInit(U(0, log2Up(entries) bits))  // 简单轮换替换

  // 命中：tag 相等（20-bit 比较）
  val hits = Vec((0 until entries).map(i => valid(i) && tags(i) === io.reqAddr(31 downto 12)))
  io.sbHit := hits.orR
  io.hitWay := OHToUInt(hits.asBits)          // 命中路（用于替换顺序）

  // 命中行数据输出（组合读，寄存器数组天然单周期可读）
  io.sbData := data(io.hitWay)

  // 预取请求分配一路
  when(io.pfAddr.fire) {
    tags(roundRobin) := io.pfAddr.payload(31 downto 12)
    valid(roundRobin) := True
    roundRobin := roundRobin + 1
  }
  // 逐 word 填充
  when(io.fillValid) {
    data(io.fillWay)(io.fillWord) := io.fillData
  }
}
```

要点：寄存器数组 = 单周期读任意 word，正好让"提升"不必插入等待；512B 用寄存器
也可换成一块 `SDPRAM(128×32bit)` + 一个读序状态机（若担心 512 触发器布线）。

## 3. 命中路径分叉（`MEM2` area，`cacheRefillFSM` 之前，约 L155-165）

现有 `hit = hits.orR`（L1 命中）。在它之后加流缓冲命中：

```scala
val sbHit = sb.io.sbHit
sb.io.reqAddr := cachePhysAddr                       // 需求物理地址
// "有效命中"：L1 命中，或流缓冲命中（后续提升）
val effectiveHit = hit || sbHit
```

`cacheRefillFSM` 的 `stateBoot`（L428-435）原本：

```scala
stateBoot.whenIsActive {
  when(reqValid && !hit) {
    arbitration.haltItself.set()
    rspId.clear()
    triggerWriteback := dirty
    goto(waitAXI)
  }
  when(isLDU) { ... goto(waitAXIU) }
}
```

改成：

```scala
stateBoot.whenIsActive {
  when(reqValid && !hit && !sbHit) {          // 真正 miss：走 AXI
    arbitration.haltItself.set()
    rspId.clear()
    triggerWriteback := dirty
    goto(waitAXI)
  }
  when(reqValid && !hit && sbHit) {           // 流缓冲命中：提升（不发 AXI 读）
    arbitration.haltItself.set()
    rspId.clear()
    triggerWriteback := dirty                 // 仍可能要先写回脏路
    goto(sbRead)
  }
  when(isLDU) { ... goto(waitAXIU) }
}
```

## 4. `cacheRefillFSM` 加 `sbRead` 状态（提升，复用 `commit`）

在 `cacheRefillFSM` 里新增一个 state，逐 word 把流缓冲行写入 `dataRAMs`，然后**复用
现有 `commit` 逻辑**（更新 tag/lru/valid/dirty）：

```scala
// 新增 state
val sbRead = new State

// 提升：读流缓冲逐 word 写 dataRAM
sbRead.whenIsActive {
  arbitration.haltItself.set()
  dataWs(replaceWay).valid := True
  dataWs(replaceWay).payload.address := idx @@ rspId
  dataWs(replaceWay).payload.data   := sb.io.sbData(rspId)   // 数据源换成流缓冲
  when(rspId === dcache.lineWords - 1) { goto(commit) }
  otherwise { rspId.increment() }
}
```

`commit` 状态（L477-504）**完全不动**——它写最后一个 word（`dataWs(...) := refillWord`）
这里要顺带改一行：把 `commit` 里最后一个 word 的数据源也按"是否提升"选择：

```scala
// commit 里原 L480-482 的最后一次写，数据源加 mux
val finalWord = Mux(从流缓冲提升, sb.io.sbData(rspId), refillWord)
dataWs(replaceWay).payload.data := finalWord
```

（用一个 `promoting = Reg(Bool())` 记录"本次是提升还是 AXI 填充"，`sbRead`/`waitAXI`
里分别置位，`commit` 里据此选数据源。简洁起见也可在 `sbRead` 最后一个 word 直接
写 `dataWs(...) := sb.io.sbData(rspId)` 再 goto `commit`，让 `commit` 的"最后 word 写"
对提升路径幂等跳过——二选一，建议用 `promoting` 标志最清晰。）

## 5. 后台预取 `prefetchFSM`（dBus 空闲时填流缓冲）

```scala
val prefetchFSM = new StateMachine {
  val sendAR = new State
  val recvR  = new State
  disableAutoStart(); setEntry(stateBoot)

  val pfWay   = Reg(UInt(log2Up(8) bits))
  val pfRspId = Counter(dcache.lineWords)
  val pfWord  = RegNext(dBus.r.payload.data)     // 预取读回 word

  stateBoot.whenIsActive {
    // 只在 dBus 空闲时启动：cacheRefillFSM 在 stateBoot 且 writebackIdle
    when(prefetchQueue.io.pop.valid && 这里的cacheRefillFSM在stateBoot && writebackIdle) {
      prefetchQueue.io.pop.ready := True
      // 分配流缓冲一路（预取请求入队时也可先分配）
      sb.io.pfAddr.valid := True
      sb.io.pfAddr.payload := prefetchQueue.io.pop.payload
      pfWay := sb.io.roundRobin                 // 与 pfAddr 分配同一路
      goto(sendAR)
    }
  }
  sendAR.whenIsActive {
    val ar = dBus.ar
    ar.payload.id := 3                          // 与需求(1)/写回区分
    ar.payload.addr := prefetchQueue.io.pop.payload(31 downto dcache.offsetWidth) @@ U(0, dcache.offsetWidth bits)
    ar.payload.len := dcache.lineWords - 1
    ar.payload.size := 2
    ar.payload.burst := 1
    ar.payload.cache := 0
    ar.valid := True
    when(ar.ready) { pfRspId.clear(); goto(recvR) }
  }
  recvR.whenIsActive {
    val r = dBus.r
    r.ready := True
    when(RegNext(dBus.r.fire)) {                 // 收到一个 word
      sb.io.fillValid := True
      sb.io.fillWay   := pfWay
      sb.io.fillWord  := pfRspId
      sb.io.fillData  := pfWord
      pfRspId.increment()
    }
    when(r.fire && r.payload.last) { goto(stateBoot) }
  }
}
```

仲裁要点：`prefetchFSM` 只在 `cacheRefillFSM.stateBoot && writebackIdle` 时才能从
`stateBoot` 进 `sendAR`，因此**需求 refill 与脏行写回天然优先**；一旦进入 sendAR/recvR，
需求 miss 因 `cacheRefillFSM` 的 `when(reqValid && !hit && !sbHit)` 会发现 dBus 被占而
自然等待（AXI 握手 `ar.ready`/`r.ready` 由 arbiter 保证）。

## 6. 预取触发（需求 miss 时入队）

在 `cacheRefillFSM.stateBoot` 的 `reqValid && !hit && !sbHit` 分支里加：

```scala
when(reqValid && !hit && !sbHit && addrCached) {
  prefetchQueue.io.push.valid := True
  prefetchQueue.io.push.payload := (cachePhysAddr + U(dcache.lineSize))
  // 只入队一次；队列满则丢弃（push.ready 为低时自然丢弃）
}
```

（`addrCached` 已有，见 `MEM2` 里 `input(ADDRESS_CACHED)`；uncached 地址不预取。）

## 7. 正确性与时序注意点

1. **store-buffer 一致性**：预取行可能落后于 store buffer 里未写回的数据。现有
   `MEM2` 的 load 前传逻辑（`storeBuffer.query` + STD 前传，L561-583）在 load 时仍
   会用最新数据覆盖 `memRData`，所以**预取数据过期不影响正确性**——这正是代码注释
   L396-397 已保证的机制。提升后 load 照常前传。
2. **dirty 写回顺序**：提升路径 `goto(sbRead)` 前仍设 `triggerWriteback := dirty`，
   与 AXI 填充路径一致（脏路先写回再覆盖）。`sbRead` 里 `arbitration.haltItself`
   会阻塞 MEM2，直到 `dirtyLineWritebackFSM` 完成——与现有 `waitAXI` 行为一致。
3. **mispredict flush**：`prefetchQueue` 与流缓冲**无需 flush**（预取是无害的，
   最坏浪费带宽）；流缓冲的 `valid` 也不用随 flush 清（tag 是物理地址，下次仍可能
   命中）。若要省带宽，可复用 `queueFlush` 清空 `prefetchQueue`。
4. **CACHE 指令（CACOP）**：`CACHEFSM` 的 `HitInvalidate/IndexInvalidate/StoreTag`
   目前只清 L1 的 `valids`；加了流缓冲后，`StoreTag`（全清）也应清流缓冲的 `valid`
   （`sb.valid.foreach(_ := False)`），避免 stale 行被提升。
5. **时序**：`sbData(rspId)` 是寄存器数组组合读 + `dataWs` 写 dataRAM，与现有
   `refillWord` 路径同构，不新增关键路径；`sbHit` 是 8 路 20-bit 比较的或归约，
   若担心时序可拍一级（代价是提升多 1 周期，`sbRead` 前插一拍）。

## 8. 面积代价

| 项 | 量 |
|----|----|
| 数据存储 | 8×16×32bit = 512B（寄存器或 128×32bit SDPRAM）|
| tag + valid + 轮换指针 | 8×20 + 8 + 3 ≈ 171 触发器 |
| 预取队列 | 8 项 × 32bit 地址 ≈ 256 触发器 |
| 比较器/mux | 8 路 tag 比较 + 一个数据源 mux（组合，可忽略）|

合计 ≈ 0.5KB 存储 + 几百触发器，相对 8KB DCache 约 5%，相对整核 <1–2%。

## 9. 若只想最小改动（方案 B：直接塞 L1，不加流缓冲）

仅需 §6 的预取触发 + 把 §3/§4 换成：在 `cacheRefillFSM` 的 `finish` 状态（或
`stateBoot` 且 `writebackIdle` 时）再触发一次对 `cachePhysAddr + lineSize` 的普通
refill。收益会低于流缓冲版（与需求 miss 串行 + 污染 L1），但代码量小一个量级。
若团队时间紧，可先落方案 B 度 1，再迭代到流缓冲版。
