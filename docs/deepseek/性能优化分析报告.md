# LA CPU 性能优化分析报告

> 基于 `cpu_model/` 对 t26-submit 分支 SpinalHDL 乱序核的 Python 性能模型。
> 所有绝对 IPC 为模型估值，**重点看相对变化**；工作负载为校准过的合成
> trace（loop / matrix / pointer_chase / call_return / branchy，覆盖 CoreMark
> 的循环、矩阵、链表、调用返回、难预测分支等行为类）。

## 1. 基线微架构（与 RTL 默认参数一致）

| 部件 | 参数 |
|------|------|
| 取指 | 4-wide；ICache 64 set × 2-way × 64B（8 KB）|
| 分支预测 | gshare（GHR 5 bit × PHT 8192×2bit）+ 直接映射 BTB 1024 + RAS 8 |
| 译码/重命名 | 3-wide；物理寄存器 63；投机 RAT + 空闲列表 |
| 发射 | 整数压缩队列 depth 7（3 口）；乘除 FIFO depth 3；访存 FIFO depth 5（**按序 head-issue**）|
| ROB | 32 项，3-wide 顺序提交 |
| 分支恢复 | **提交时重定向**（mispredict 需等到分支走到 ROB 头才 flush）|
| DCache | 64 set × 2-way × 64B（8 KB），写回 + 写分配 |

## 2. 基线性能

| 工作负载 | IPC | 误预测率 | DCache MPKI | 瓶颈 |
|----------|-----|---------|-------------|------|
| loop_bench（流式读）| 0.52 | 0.1% | 19.2 | DCache 流式缺失 + 按序访存 |
| matrix（嵌套循环）| 0.59 | 12.7% | 16.8 | 循环退出误预测 + 2-way 冲突缺失 |
| pointer_chase | 1.48 | 0.0% | 0.3 | —（缓存友好）|
| call_return | 0.74 | 11.1% | 0.0 | 调用/返回预测 |
| branchy（难预测分支）| 0.55 | 24.4% | 7.4 | 数据依赖分支 + 提交时重定向 |
| **合计** | **0.69** | **11.0%** | **7.4** | |

## 3. 分支预测分析

| 配置 | 合计 IPC | 合计误预测率 | 备注 |
|------|---------|-------------|------|
| 基线（h=5）| 0.686 | 11.0% | |
| h=8 / h=10（PHT 不变）| 0.655 / 0.663 | 12.4% / 10.9% | call_return 反而变差 |
| h=12（PHT 不变）| **0.383** | **42.8%** | **索引别名灾难** |
| PHT 16K / 32K | 0.686 | 11.0% | 无变化（PHT 不是瓶颈）|
| BTB 2K / 4K / 2-way | 0.686 | 11.0% | 无变化（BTB 已够用）|
| RAS 16 / 32 | 0.686 | 11.0% | 无变化（调用深度 ≤6）|
| h=12 / PHT=64K | 0.642 | 11.2% | 别名缓解但无增益 |
| combo（h=10/PHT=16K/BTB=2K2w/RAS=16）| 0.663 | 10.9% | 收益很小 |

**结论**：
1. 单纯加大 GHR 位宽而**不同步放大 PHT**会灾难性变差（PHT 索引 `GHR @@ PC[9:2]`
   的 PC 位被挤掉，h=12 时只剩 1 个 PC 位 → 不同分支站点互相别名）。
2. 这些工作负载的剩余误预测**不是 gshare 容量问题**，而是结构性问题：
   - matrix 的 16 次循环退出（`T×15 N` 模式需要 ≥16 bit 历史才能学，gshare 学不了）；
   - branchy 的真随机数据依赖分支（任何 gshare 都学不了）；
   - call_return 的调用/返回交互。
   所以 h/PHT/BTB/RAS 增大在这些负载上收益**有限**（合计 IPC 最多 +0～-2%）。
3. 要突破，需要**结构改进**而非参数调大：
   - **循环预测器（loop predictor）** 直接学循环退出（针对 matrix 类）；
   - **TAGE / 感知器** 提升难预测分支（针对 branchy 类）；
   - 更重要的见下——**把提交时重定向改成执行时重定向**。

## 4. 缓存分析

| 配置 | 合计 IPC | 合计 DCache MPKI | loop_bench IPC | matrix IPC |
|------|---------|------------------|----------------|------------|
| 基线（I/D 4KB 2-way）| 0.686 | 7.41 | 0.52 | 0.59 |
| I/D 4KB **4-way** | 0.703 | 6.38 | 0.52 | **0.84** |
| I/D 8KB / 16KB 2-way | 0.686 | 7.41 | 0.52 | 0.59 |
| line=32B | 0.593 | 13.9 | 0.38 | 0.55 |
| 基线 + **prefetch** | **0.783** | **1.19** | **0.81** | 0.59 |
| 基线 + LSU OoO | 0.686 | 7.41 | 0.52 | 0.59 |
| **16KB 4-way + prefetch + LSU OoO** | **0.808** | **0.02** | 0.81 | 0.89 |

**结论**：
1. **下一行（next-line）预取是缓存侧最大收益**：合计 IPC +14%（0.686→0.783），
   流式读（loop_bench）IPC +56%（0.52→0.81），DCache MPKI 从 7.4 降到 1.2。
   因为流式访存每 64B 行只缺一次（6.25%），预取把下一次的缺失提前隐藏。
2. **4-way 相联度修复 matrix 的冲突缺失**：matrix IPC +42%（0.59→0.84）。
   A/B/C 三个数组地址低位相同 → 同 index，2-way 放不下第三路，每轮迭代冲突；
   4-way 全部容纳。真实代码中若数组对齐不佳会复现同类问题。
3. 单纯加大容量（8KB/16KB 但保持 2-way）对这些负载**无收益**（容量已够，缺的是相联度/预取）。
4. line=32B 变差（缺失次数翻倍），不建议。
5. **单独放宽 LSU 按序（OoO）无收益**：因为单次缺失仍通过按序 refill 阻塞整条访存流水。
   要叠加**非阻塞 Cache（MSHR）**才能让多个缺失重叠，与 OoO 一起才有效。

## 5. 后端（ROB）分析

| 配置 | 合计 IPC | branchy IPC | call_return IPC |
|------|---------|-------------|-----------------|
| 基线（ROB=32）| 0.686 | 0.554 | 0.739 |
| ROB=64 | 0.596 | 0.415 | 0.569 |
| ROB=64 + IQ=14 | 0.611 | 0.459 | 0.537 |
| ROB=64 + IQ=14 + retire=4 | 0.619 | 0.460 | 0.563 |

**结论（重要）**：**在提交时重定向的设计下，加大 ROB 反而伤害分支密集型代码**
（branchy 0.554→0.415，call_return 0.739→0.569）。原因是 mispredict 的恢复要等
分支走到 ROB 头，ROB 越深，被错误路径指令填得越多、被 flush 的浪费越大，误预测
代价与 ROB 深度成正比。**这再次印证：当前最大结构性瓶颈是提交时重定向。**

## 6. 优化建议（按优先级）

### P0 — 把提交时重定向改为执行时重定向
- 现象：ROB 增大反而变慢；branchy（24% 误预测）IPC 仅 0.55；误预测代价随 ROB 深度放大。
- 做法：BRU 在 EXE 算出 mispredict 后**立即**驱动 `backendJumpInterface` 冲刷前端，
  而不是等 commit。需要在 ROB 加分支 checkpoint（恢复 sRAT/空闲列表/GHR/RAS），
  或复用现有 `regFlush` + `recoverPRF` 机制提前触发。
- 预期：把误预测代价从「ROB 排空 + 重取」降到「流水深度 + 重取」（约 5–10 拍）。
  分支密集型（CoreMark 状态机/链表）收益最大，且解除了「ROB 不能加大」的限制。

### P1 — 加下一行流预取（ICache + DCache）
- 现象：合计 IPC +14%，流式 IPC +56%，DCache MPKI 7.4→1.2，几乎零面积代价。
- 做法：访问地址命中时，对 `addr + line_size` 发一个后台预取（无副作用地填入
  未命中的下一行），复用现有 refill FSM 或加一个轻量 prefetch 状态机。
- 注意：需避免污染（可加一个 prefetch 到专用路/小队列）。

### P2 — DCache 相联度 2→4（或更高）或改进数组布局
- 现象：matrix 因 A/B/C 同 index 冲突，IPC +42%（0.59→0.84）。
- 做法：DCache 由 2-way 改 4-way（当前 VIPT 4KB 限制内可行），或软件侧对齐数组。
- 成本：tag/数据 SRAM 翻倍，但对 105MHz 时序友好。

### P3 — 非阻塞 Cache（MSHR）+ 放宽按序访存
- 现象：单独 OoO 访存无收益，因为单次缺失阻塞整条访存流水。
- 做法：给 DCache/ICache 加 1–2 个 MSHR，允许多个缺失并行 refill；
  访存队列从 head-issue 改为可 OoO 发射（需要内存序/存储缓冲正确性检查）。
- 预期：与预取叠加后（16KB4w+prefetch+OoO）合计 IPC 0.69→0.81，MPKI→0.02。

### P4 — 分支预测结构升级（优先级低于 P0，收益被 P0 掩盖）
- 当前 5-bit gshare 在嵌套循环（12.7%）、调用返回（11.1%）、难预测分支（24.4%）仍有误预测。
- 不要盲目加历史位：必须历史位与 PHT 同步放大，否则 h=12 会别名崩溃（IPC 0.38）。
- 更有效的是**循环预测器**（学循环退出）+ **TAGE**（提升难预测分支），
  以及确保 RAS 的恢复与重定向时机一致。

## 7. 建议落地顺序（单次迭代收益最大）

1. 执行时重定向（P0）+ 下一行预取（P1）——两者互不冲突，改动中等，收益最大。
2. DCache 4-way（P2）——若 CoreMark 实测有冲突缺失。
3. 非阻塞 Cache + OoO 访存（P3）——访存型基准的提升天花板。
4. 循环/TAGE 预测器（P4）——在 P0 落地后再评估，避免被重定向代价掩盖。

## 8. 局限与后续

- 工作负载为**校准过的合成 trace**，非 CoreMark 真实二进制；接入真实 trace 只需
  把 benchmark 交给 `cpu_model/funcsim.py` 生成 `TraceRecord` 序列。
- 内存时延为可调参数（`MemoryConfig.dram_latency`，默认 20 + 16 beat）；不同
  存储子系统下绝对 IPC 会平移，但相对结论不变。
- TLB / 异常 / 中断 / uncached / store buffer 细节按稳态忽略。
- `early_redirect` 已在模型中实现为实验项，但 RAS 重取时序需进一步校正，
  故 P0 的量化采用解析估计（见上），建议在 RTL 上以 difftest 验证。
